4.2High-level system architecture

The key architectural idea is that Zebrain's servers do no GPU work. They orchestrate: check accounts, push a self-contained Python job to the user's Kaggle, and read its progress from the user's Hugging Face state repo. The job writes everything it knows (progress, checkpoints, versions, test sets, the open chat's URL and API key) into that private repo, which makes runs resumable and the web app nearly stateless.

4.3Frontend

  • Routes: / (home, FAQ), /pricing, /login, /connect (Kaggle, HF, Gemini keys), /new (wizard), /runs (progress), /chat (dashboard, owner chat, API guide), /fix (corrections, identity, versions, Testify). Verified
  • Live model access: lib/gradio.ts loads the matching @gradio/client from a CDN at runtime (1.5.2 for Gradio 4/5, 2.7.1 for Gradio 6) and streams replies with client.submit. Verified
  • State: server data comes from API routes. There is no client-side store library. Runs are polled from /api/runs/status.
  • Recommendation Pin the CDN client with Subresource Integrity, or bundle it, so a CDN compromise cannot run code on Zebrain pages.

4.6Database schema, relationships and lifecycle

  • Indexes: runs has a unique constraint on (user_id, run_id, kernel), used by the upsert that resumes runs. Recommendation Add runs(user_id, started_at desc) for the runs list.
  • Unused tables: four token-gateway tables and three functions (reserve_tokens, settle_tokens, rebalance_tokens) from a paused build. Recommendation Either finish the gateway or drop them, so the schema documents only what is real.
  • Proposed launch tables: subscriptions (plan, status, period, gateway ids), invoices, credits (GPU-hours ledger), hosted_models (model, version, endpoint, plan), api_keys (hash, prefix, scopes, last_used), usage_events (model, messages, tokens, day, partitioned by month), orgs, memberships, audit_log.
  • Data lifecycle: run rows are kept for the account's lifetime. Usage events are rolled up to daily after 90 days. Deleted accounts are purged within 30 days and their stored keys are deleted immediately (§4.12).

4.8Background jobs, serving and the proposed hosting platform

Today the "queue" is Kaggle itself: each run is a Kaggle script session, at most 2 GPU sessions per Kaggle account. The web app polls status. Turning a chat offline works by writing a signal into control.json, which the job checks every 30 s, because Kaggle offers no reliable external cancel. Verified

Serving quality safeguards (built): replies stream token by token. Up to 1,536 new tokens per pass, and a reply that hits the cap continues automatically (up to 3 passes). A light repetition penalty (1.05) prevents loops. Before a reply is final, a checker looks for runaway encoded strings (e.g. data URLs, stopped as they start), unclosed code blocks, unbalanced brackets, Python syntax errors and over-length code when the user set a line limit. A failing answer is rewritten once, and is flagged if it still fails. Verified

Proposed scheduled tasks: nightly usage roll-up and quota reset at period start (cron); a daily check for stuck runs (Kaggle status stale over 2 h → notify the user); weekly key-age reminders; monthly invoice reconciliation against gateway webhooks.

4.10Security: secrets, encryption, limits, backups and incidents

Gap: fix before launch

Users' Kaggle keys, Hugging Face tokens and Gemini keys are stored as plain text columns in connections (protected by row-level security, but not encrypted by the application) [2]. In addition, the HF token and Gemini key are embedded in each user's private Kaggle script so the job can publish and grade [1]. A leaked script or database dump would expose working credentials.

4.11Performance, scalability, reliability and cost

  • Web tier is stateless and scales horizontally. The heaviest route, /api/plan, is dominated by Gemini latency (probe 15 s, real calls up to 150 s). Recommendation Move it to a background job with progress events instead of one long request.
  • Training scales with users for free, because each user brings their own Kaggle GPU. Paid training scales with the GPU budget, through a queue with per-user concurrency limits.
  • Chat latency: streaming made the first words appear about 200 ms after submit in local tests (versus waiting for the whole reply before). Verified (local Gradio 6 test)
  • Cost levers for hosting: multi-LoRA on shared base models, 4-bit or 8-bit inference for ≤3B, scale-to-zero for Starter and warm pools for Pro, and response caching for repeated FAQ answers.
