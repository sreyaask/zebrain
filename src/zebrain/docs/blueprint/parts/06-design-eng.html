5.1Brand identity and design principles

Zebrain's interface uses a black page, a single brand blue, the Inter typeface, a pixel font (Silkscreen) for the wordmark and accents, a blue "light beam" gradient in the hero, pill-shaped buttons and chat bubbles styled like Gradio's. Verified (tailwind.config.ts, globals.css, layout.tsx) No logo file or brand guideline document exists. Unknown This chapter codifies what the product already does. Anything new is marked as a recommendation.

One colour

Blue #3d7bff is reserved for action and focus: buttons, focused links, the beam. Never decoration.

Plain words

Labels say what happens ("Train on Kaggle", "Turn offline"). No AI jargon in primary UI.

Show the proof

Scores, before/after answers and logs are first-class UI, because trust comes from evidence.

Logo and wordmark usage

Recommendation Until a designed logo exists, the wordmark is the word zebrain set in Silkscreen, lower-case, in paper white on black or black on white. Keep clear space of at least the height of the "z" on all sides. Do not stretch it, outline it, add gradients to the letters, or set it in any other font. Commission a proper logo (mark + wordmark) before paid marketing begins, and check trademark availability first (§9.2).

5.7States, accessibility and design handoff

  • Loading: say what is happening ("Gemini is reading sample rows… up to 2 minutes"). Never use a spinner without words for waits over 2 s.
  • Errors: say what went wrong and what to do, in one sentence, next to the cause. API errors already follow this pattern. Verified
  • Success: state the result and the next step ("Saved. 3 corrections waiting on the Fix page").
  • Edge cases: chat closed mid-reply, Kaggle quota exhausted, gated model not accepted, Gemini overloaded, HF read-only token. Each gets a specific message.
  • Accessibility: keyboard reachable everything, visible focus rings, aria-live on streaming chat and status, labelled inputs, prefers-reduced-motion respected, targets of 40 px or more on touch.
  • Handoff: tokens live in tailwind.config.ts, which is the single source. Design files mirror the token names exactly. Each component has a short doc (purpose, props, states, accessibility notes) next to its code. Recommendation
  • Frontend standards: server components by default, client components only for interactivity, no new UI library without a decision record, and every page must pass a 360 px width check and keyboard-only use before merge.

Why data generation ranks above more training rounds: in the internal coding-model run, extra rounds moved the held-out test score only from 38% to 42% and plateaued, while 25-question exams can't cover a domain. Small models are data-limited. Producing about 2,000 high-quality, task-specific examples per job is the biggest quality lever. Verified (internal run) + Recommendation

6.2Requirements, user stories and development cadence

  • Methodology: two-week cycles (lightweight Scrum), plus a continuous-flow lane for bugs. Justification: one to four engineers, fast-changing external APIs, and a need for a weekly demo on real models.
  • Every feature starts with a 1–2 page PRD (Appendix A5): problem, users, success metric, scope / out of scope, user stories, acceptance criteria, risks, rollout.
  • User story format: "As a shop owner, I want to fix one wrong answer from the chat, so that the next version answers correctly."
  • Acceptance criteria in Given/When/Then. Example: Given a saved correction, when I start a fix run, then the published version answers the corrected question correctly and no earlier test score drops by more than 2 points.

6.3Environments, branching, reviews and release management

  • Branching: trunk-based. Short branches feat/…, fix/…, merged by squash after review. main is always deployable.
  • Pull requests: under 400 lines where possible. The description covers what, why, screenshots and test evidence. One approving review, two for auth, keys, billing or the training job's publish logic.
  • Releases: continuous deployment of the web app from main behind feature flags. The training job is versioned (JOB_VERSION), and each run records which version it used, so a regression can be traced to a job release.

Release checklist

  • CI green: typecheck, lint, build, Python job tests
  • Staging canary run completed all stages on a test Kaggle account (for job changes)
  • Database migrations reviewed, reversible, and applied to staging first
  • Feature flag default set. Rollback plan written in the PR.
  • Changelog entry and docs/API guide updated
  • Error-rate and run-failure dashboards watched for 30 minutes after deploy

6.6Technical debt and documentation standards

  • Keep a debt register in the tracker, tagged debt, and spend 15–20% of each cycle on it. Current known items: unused token tables, train-mode retrain skill replay, the CDN client without SRI, plaintext key columns, /api/plan as a long request, booking-link placeholder, no Git history.
  • Documentation: README for setup, this manual for operations, decision records for one-way doors, and docstrings that explain why (the codebase already does this well). Verified

6.7User feedback, analytics and experimentation

  • In-product feedback: the "Wrong answer?" and correction flow is also a feedback channel. Add a 1-click "Was this run useful?" after each publish.
  • Analytics events (privacy-friendly, no message content): signup, connect_completed{service}, plan_requested, run_started{mode}, run_finished{stage, scores}, chat_opened, api_called, correction_saved, checkout_started, subscribed{plan}.
  • Experiments: one at a time on the onboarding funnel. Write the hypothesis and the minimum detectable effect first, and run each test for at least 2 weeks or until it reaches its planned sample size.
